# Directive: Preview Design Systems

## Goal

Let the user see rendered HTML before committing — either brand design systems from
`awesome-design-md` (the whole catalog at a glance, or full-page mockups of specific
brands, or font/accent variants), or, for XoXoCom specifically, candidate hero shapes,
candidate full-page layouts for pages that don't exist yet, candidate favicon/tab
marks for the identity system, and — once a layout direction is chosen — a copy-free
content spec for that direction. For the brand modes, this is the visual front end to
step 1 of `design_website.md`: browse, pick a brand, then build the real site with
that brand's `DESIGN.md`. For the XoXoCom-specific modes (origami shape lab, page
prototype lab, logo lab, chosen-pages content-spec round), it's a way to choose a
direction — and then pin down exactly what a human still has to write — before any
Next.js route, hero component, or favicon is written or changed.

## Inputs

Ask which mode the user wants; do not assume:

- **Catalog gallery** — one page with a small live card for every brand. No input needed. Best for "show me everything / help me choose."
- **Per-brand full-page preview(s)** — a complete one-page marketing mockup per brand. Input: **one or more brand names** (e.g. `stripe`, or `stripe, linear, vercel`). Best for "show me what a site in <brand>'s style looks like." The user may request a single brand or several at once.
- **Font lab** — side-by-side typeface comparison using a single brand's color tokens. Input: **one brand name**; optionally a comma-separated list of Google Font names.
- **Accent lab** — side-by-side accent-color comparison using a single brand's canvas and ink. Input: **one brand name**; optionally a comma-separated list of `Name:#hex` pairs.
- **Origami shape lab** — a review page for a family of translucent folded-paper geometric shapes intended for the XoXoCom hero animations. No input needed by default; optionally the facet-opacity range, crease opacity, and silhouette-outline opacity can be tuned.
- **Page prototype lab** — side-by-side full-page layout prototypes for new XoXoCom pages (currently About and Press/Media) so a direction can be chosen before any Next.js route is written. No input needed; the only tunable is the output folder.
- **Chosen-pages content spec** — the follow-up to the page prototype lab, once a direction has been picked for each page. Renders only the chosen layouts, with every piece of copy a human must still write replaced by a labeled slot (the checklist's own template plus a length spec) instead of drafted prose. No input needed; the only tunable is the output folder. Which two directions are "chosen" is hardcoded in the script (currently About = A2 "Company dossier", Press & Media = P2 "Press kit first" — Option 2 in both rounds) — changing the choice means editing the script's `PAGES` list *and* its `about()`/`press()` builders, not passing a flag.
- **Logo lab** — a review page for four provisional favicon/tab-mark candidates (twin, interlock, fused, wordmark), all drawn from the same two-X rule, so a mark can be judged before it is wired in as the site favicon. No input needed by default; optionally the stroke width, overlap amount, gap, clearance, fused-variant opacity, line cap, icon padding/corner radius, icon background, accent color, wordmark weight, wordmark tracking, and wordmark ink color can be tuned.

Brand names are resolved leniently (`linear` → `linear.app`, `mistral` → `mistral.ai`), so pass what the user typed. The full brand list is the 74-entry catalog in the `awesome-design-md` SKILL.md (also printed by any script on an unknown name).

## Tools / Scripts

- `execution/preview_design_systems.py` — renders the **catalog gallery** of all 74 brands to one self-contained HTML file. Each card shows the brand in its own canvas/ink/accent, a light/dark badge, the description, palette swatches, and a live filter box. Card title = the exact `--design-source` value.
- `execution/build_brand_preview.py` — renders a **full-page preview** (header, hero, trust strip, feature grid, stats band, CTA, footer) per brand, each as its own self-contained HTML file. Accepts `--brands <csv>` or `--all`; writes a contact-sheet `index.html` when more than one brand is built.
- `execution/build_font_lab.py` — renders a **font lab**: holds a chosen brand's canvas/ink/accent tokens fixed and shows the same contextual specimen (eyebrow, headline, subhead, body, buttons) side by side in multiple candidate Google Fonts, so the user can pick a typeface that differentiates their site from the source brand while keeping its color/feel. Accepts `--design-source` (required), `--fonts "Sora,Manrope,Inter"` (default: curated 10), `--headline`, `--eyebrow`.
- `execution/build_accent_lab.py` — renders an **accent lab**: holds a chosen brand's canvas and ink fixed and swaps the accent across multiple candidate colors, each shown in context (eyebrow, headline accent word, CTA, link, stat figures) with hex labeled and contrast auto-checked. Accepts `--design-source` (required), `--accents "Indigo:#6366F1,Emerald:#10B981"` (default: curated 5), `--headline`, `--eyebrow`.
- `execution/design_md_lib.py` — shared parser + color-role derivation used by the first three scripts (not run directly).
- `execution/build_origami_lab.py` — renders an **origami shape lab**: generates ten translucent folded-paper SVG shapes (a disc, hex flower, triangle, two twist rosettes, a 3D gem, a pleat band, a chevron stack, a drifting-shards cluster, and a crane) and a preview page showing the whole family in both brand tints, an opacity ladder, a two-tint overlap demo, and three in-situ hero mock-ups using the site's real hero copy/scrim/glow. Every shape is painted in `currentColor` with translucency baked into per-facet `fill-opacity` (not a wrapper opacity), so one SVG file serves both tints (coral accent, white accent) — no per-tint duplicates. Std-lib only, deterministic (same flags in, byte-identical files out). Flags: `--assets-dir` (default `assets/origami`), `--out` (default `.tmp/origami_lab`), `--fill-min` (0.05), `--fill-max` (0.24), `--crease` (0.30), `--edge` (0.62). Unlike the other three labs, this one is not brand-parametric — its color tokens and hero copy are hardcoded to XoXoCom's canvas/ink/accent and are not driven by the `awesome-design-md` library.
- `execution/build_page_prototypes.py` — renders a **page prototype lab**: six full-page prototypes for two not-yet-built XoXoCom pages — three About directions (A1 "Founder letter": single-column narrative with the boilerplate as an opening pull-quote; A2 "Company dossier": section rail, labelled boilerplate, three equal people cards, a fact table; A3 "Founder-led": portrait+quote hero, alternating principle bands, a product-screenshot slot, three team cards) and three Press/Media directions (P1 "Newsroom": boilerplate with working copy buttons, a full fact table, asset tiles, people with an explicit "quote for" line, suggested topics, a press contact block, and an empty "as featured in" section; P2 "Press kit first": one `.zip`-download hero, logo shown on light and dark, individual assets, facts and boilerplate side by side; P3 "Reporter's cheat sheet": monospace fact keys, pre-written quotes marked draft/needs sign-off, topics paired with who to quote, and a rail with the press contact and kit download). Every prototype is wrapped in the site's real header and footer so it reads as a page. Flags: `--out` only (default `.tmp/page_prototypes`). Std-lib only, deterministic. Facts already confirmed (legal name, seat, register, Geschäftsführer, product, services) are hardcoded as real content, matching `sites/xoxocom/content/impressum.md` and `sites/xoxocom/lib/copy.ts`; everything unconfirmed renders as a visually marked `[ placeholder ]`. Like the origami lab, this script is XoXoCom-specific, not brand-parametric — updating the hardcoded facts (or their placeholders) requires editing the script's content constants directly.
- `execution/build_chosen_pages.py` — renders the two chosen page directions in **two modes** (`--mode present`, the default, and `--mode spec`), both using the same layouts: About = A2 "Company dossier" and Press & Media = P2 "Press kit first", i.e. Option 2 in both rounds. The About page keeps A2's layout but takes its closing CTA heading from A1 ("Tell us what you're trying to change.") in place of A2's "Work with us" — the one cross-prototype mix wired in. It imports `build_page_prototypes.py` directly (`import build_page_prototypes as lab`) to reuse its layout CSS, page chrome (`chrome`, `footer_bar`, `avatar`, `copy_block`, `dl_tile`), its Manrope-inlining helper (`manrope_face`), its CSS function (`css`) and its verified-fact constants, so the two files cannot drift apart; it defines its own `full_document`/`fragment_document` and an `EXTRA_CSS` block.
  - **`--mode present` (default) — the prototype you show someone.** No slots, no templates, no length specs, no process notes, no provenance, and none of the checklist's vocabulary (the press page's "Boilerplate" section is titled "About the company" with "Short version" / "Long version" blocks). Every sentence is copy already published on www.xoxocom.net — the `LIVE COPY` block at the top of the script names the `lib/copy.ts` key behind each one (`ueberUns.title`, `home.heroSub`, `ueberUns.body`, `home.aboutTitle`, the three `home.leistungen` bodies, `produkte.products[0]`, `kontakt.intro`) — or a fact from `content/impressum.md`. The two company descriptions are assembled from those facts alone. Where a fact is genuinely unknown the element is left out rather than guessed: no founding year (so no `Founded` row), no product-status claim (the live site says "Try it now"), no consulting track record and no Credibility section, no press-kit file size or date, no "As featured in" block, and no LinkedIn URLs. Two of the three team cards lead with the role instead of inventing a name, since only the Geschäftsführer is on the public record. Photography, the press-kit zip and the product screenshot stay as neutral grey placeholders.
  - **`--mode spec` — the internal working document.** Every writable block renders as a slot with the checklist's own template and a length spec, plus the notes, the eight-row `FACT_BANK`, the Credibility section and the hand-off markers. This is the mode that tracks what is still missing; it is not the mode you present.
  - Mechanics: `PRESENT` is a module global set from `--mode` in `main()`, and every text helper is mode-aware — `slot(tag, template, spec, scale, real)` renders the slot in spec mode and `real` (or nothing at all) in presentation mode; `val(label, real)`, `fact(text)`, `note(text)` and `spec_only(html)` follow the same pattern, with `note`/`spec_only` collapsing to nothing when presenting. **Anything that calls these helpers must be built lazily** (see `team_spec()`, `press_assets_spec()`, `press_facts_spec()`): a module-level constant would freeze the wrong mode at import time, before `main()` sets it. Flags: `--mode`, `--out` (default `.tmp/chosen_pages`). Std-lib only (aside from importing the sibling script), deterministic.
- `execution/build_logo_lab.py` — renders a **logo lab**: generates four provisional favicon/tab-mark candidates, all drawn from the same two-X rule so they read as one family — `twin` (the current wordmark reduced to its two accent-bearing X glyphs, side by side; wide, aspect ~2.14:1, so it shrinks hard in a square icon), `interlock` (the two X's overlapped and woven so the pair crosses at exactly two points, one X passing over the other at each — a true interlace, symmetric under a 180° rotation about the overlap centre, so "neither X overshadows the other" is a property of the geometry rather than a judgement call; aspect ~1.38:1), `fused` (the same overlap painted instead of woven — both X's translucent at a default stroke-opacity of 0.72 so the shared region reads brighter; nothing is cut and nothing stacks, so it is the variant that survives 16 px intact), and `wordmark` (the full "XoXoCom" logo exactly as the site header sets it today — both X's coral, every other letter ink, per the rule in `XOXOCOM_BLUEPRINT.md` §3.2). Unlike the other three, which are pure stroke geometry, the wordmark is type: its glyphs are outlined from the site's Manrope variable font subset using `fontTools` (`instantiateVariableFont` pinned to `--wordmark-weight`, default 800, matching the header's `font-extrabold`) via `SVGPathPen` + `TransformPen` (y-flip into SVG space) + `BoundsPen` (tight ink bounding box), so the resulting SVG has no font dependency at render time — it works as a favicon or in an `<img>` with Manrope not installed, and the outlined file is small (~2.6 KB). `fonttools>=4.50.0` and `brotlicffi>=1.1.0` (brotli lets fontTools decompress the `.woff2`) are optional, build-time-only dependencies listed in `requirements.txt`; if either is missing, or `--font` is unreadable, the script prints a warning, skips only the two wordmark asset files, omits Option D from the lab page, and notes the skip in the spec table — it does not crash. The wordmark's glyphs carry the accent internally (on the X's) and leave the rest as `currentColor`, so — unlike the three stroke marks, which are tinted with the accent — it must be tinted with the ground's ink color or the non-X letters vanish; the lab page handles this with a per-mark `tint` role. Its lockup view differs too: since the wordmark is already a lockup, the pairing shown is wordmark + legal suffix "UG" rather than mark-plus-name. Measured finding the lab page states outright: the wordmark's aspect ratio is far too wide (~6.26:1) to work as a favicon — the letters go sub-pixel well before 16 px — so it is included as the correct mark for a header, email signature, or share image, not for the tab slot. Writes tintable `currentColor` monogram SVGs plus square icon SVGs with explicit fills (a favicon inherits no CSS), an annotated interlace-crossing proof diagram, and a lab page comparing all four at true tab pixel sizes (16/20/32/48 px) in both dark and light browser chrome, plus monogram/icon/lockup views and a measured specs table (contrast ratios, crossing coordinates, rotation centre, wordmark aspect ratio). Std-lib only for the three stroke marks; deterministic overall (same flags in, byte-identical files out, including the outlined wordmark). Flags: `--stroke` (0.20), `--overlap` (0.62), `--gap` (0.14), `--clearance` (0.26), `--fused-opacity` (0.72), `--wordmark-weight` (800), `--tracking` (-0.02 em, matching the header's `tracking-tight`), `--wordmark-ink` (default `#eaecef`), `--linecap` (round), `--icon-pad` (0.12), `--icon-radius` (0.22), `--icon-bg`, `--accent`, `--assets-dir` (default `assets/logo`), `--out-dir` (default `.tmp/logo_lab`), `--font`. Like the origami and page-prototype labs, this script is XoXoCom-specific, not brand-parametric — its brand tokens mirror `sites/xoxocom/app/globals.css` directly.
- `browser-harness` (global CLI) — optional, to open a preview and screenshot it for the user.

No API tokens or `.env` required — all scripts read the local library only.

## Process

### A. Catalog gallery (browse everything)

1. Run `python execution/preview_design_systems.py`.
2. It writes `.tmp/awesome_design_gallery/index.html` and prints a `file://` URL.
3. Give the user the path/URL (optionally open + screenshot via `browser-harness`). They filter by brand or vibe ("dark", "fintech", "editorial", "green") to narrow down.

### B. Per-brand preview(s) (on demand)

1. Confirm the brand name(s) the user wants. One or many.
2. Run:
   - single: `python execution/build_brand_preview.py --brands stripe`
   - several: `python execution/build_brand_preview.py --brands stripe,linear,vercel`
   - all: `python execution/build_brand_preview.py --all`
3. Each preview is written to `.tmp/brand_previews/<brand>/index.html`. When more than one is built, a contact-sheet `.tmp/brand_previews/index.html` links them all.
4. Hand the user the `file://` URL(s) the script prints (optionally open + screenshot the top + a lower section via `browser-harness` so they see it inline).
5. When the user picks a brand to actually build with, proceed to `design_website.md` step 1 using that brand as `--design-source`.

### C. Font lab (differentiate the typeface)

Use this after a brand's colors are chosen but before committing to a display font. The lab renders the brand's canvas/ink/accent unchanged and cycles through candidate Google Fonts so the user can see which typeface fits without requiring the source brand's proprietary font.

1. Confirm the brand name. Ask if the user has specific fonts in mind; if not, use the script's curated 10.
2. Run:
   - default fonts: `python execution/build_font_lab.py --design-source binance`
   - specific fonts: `python execution/build_font_lab.py --design-source binance --fonts "Sora,Manrope,Inter"`
   - custom copy: add `--headline "Your tagline here."` and/or `--eyebrow "Your company"`
3. The script writes `.tmp/font_lab/<brand>/index.html` and prints the `file://` URL. Hand the URL to the user (optionally screenshot via `browser-harness`).
4. When the user selects a font, record it as the `--display` font family in `design_website.md`.

### D. Accent lab (differentiate the accent)

Use this when the user wants the source brand's canvas and ink but a different accent color — for example, keeping a near-black/white palette while swapping away from a branded yellow. Each candidate is shown in context with auto-checked contrast.

1. Confirm the brand name. Ask if the user has specific accent colors in mind; if not, use the script's curated 5.
2. Run:
   - default accents: `python execution/build_accent_lab.py --design-source binance`
   - specific accents: `python execution/build_accent_lab.py --design-source binance --accents "Indigo:#6366F1,Emerald:#10B981"`
   - custom copy: add `--headline "Your tagline here."` and/or `--eyebrow "Your company"`
3. The script writes `.tmp/accent_lab/<brand>/index.html` and prints the `file://` URL. Each specimen shows the hex code and confirms the contrast ratio. Hand the URL to the user.
4. When the user selects an accent, record it as the accent token override in `design_website.md`.

### E. Origami shape lab (XoXoCom hero shape review)

Use this when reviewing candidate folded-paper geometric shapes for the XoXoCom hero animations, before any shape is wired into a hero component.

1. Confirm whether the user wants the default translucency settings or a custom facet-opacity/crease/edge tuning.
2. Run:
   - default: `python execution/build_origami_lab.py`
   - custom tuning: `python execution/build_origami_lab.py --fill-max 0.28 --crease 0.4`
   - custom asset location: `python execution/build_origami_lab.py --assets-dir assets/origami`
3. The script writes each shape to `assets/origami/<shape>.svg` (durable, hand-editable assets, not `.tmp/`) and writes the preview page to `.tmp/origami_lab/index.html`, plus a body-only fragment at `.tmp/origami_lab/artifact.html` for publishing as a Claude artifact. Hand the user the `file://` URL or the artifact link.
4. When the user picks shapes and a motif strategy (one shape everywhere vs. per-page, and whether shapes replace or layer behind the existing hero canvas components), record the decision and proceed to wiring the chosen SVGs into the relevant hero component(s) under `design_website.md`.

### F. Page prototype lab (About and Press/Media layout directions)

Use this when a new page for XoXoCom needs a content structure and layout decided before any Next.js route is written — currently the About page rewrite and a new Press/Media page. Follows the build order in the source checklist (`website-about-press-checklists.md`, supplied by the user, not committed to the repo): lock the boilerplate first since every other surface reuses it verbatim, then About, then Press, then founder sign-off, then outreach.

1. Confirm which placeholder facts the user wants to fill in before generating (founding year, the founder's single title used consistently everywhere, his years of experience/specialisation, the user's own name/title as it should appear in print, the product lead's name, client types, and who the press contact is). If any remain undecided, proceed anyway — unresolved facts render as a visually marked `[ placeholder ]`, which is the point of the lab.
2. Run: `python execution/build_page_prototypes.py` (or `--out <path>` for a custom location).
3. The script writes `.tmp/page_prototypes/index.html` (standalone) and `.tmp/page_prototypes/artifact.html` (body-only fragment for publishing as a Claude artifact). Hand the user the `file://` URL or the artifact link.
4. Get the user's decision: which About direction (A1/A2/A3) and which Press direction (P1/P2/P3) to build, noting that mixing elements across prototypes is cheap (e.g. A2's fact table into A1, P3's quote block into P1). Also get sign-off on any drafted-but-unapproved content the prototypes surface (suggested podcast/interview topics, quote-ready statements marked "needs sign-off").
5. Once a direction and the remaining placeholders are confirmed, proceed to writing the real Next.js route(s) under `design_website.md` — the About rewrite replaces `components/content/UeberUnsContent.tsx`; the Press page is new (route, nav/footer entry) and has no prior directive step, since no directive yet covers adding a page outside the site's four-page template.

### G. Logo lab (XoXoCom favicon/tab-mark review)

Use this when reviewing candidate favicon/tab marks for the XoXoCom site, before any mark is wired in as the actual favicon.

1. Confirm whether the user wants the default geometry or a custom stroke/overlap/gap/clearance/opacity/icon tuning.
2. Run:
   - default: `python execution/build_logo_lab.py`
   - custom tuning: `python execution/build_logo_lab.py --stroke 0.24 --overlap 0.55`
   - custom asset location: `python execution/build_logo_lab.py --assets-dir assets/logo`
3. The script writes each candidate's monogram and icon SVGs, plus the interlace-proof diagram, to `assets/logo/` (durable, hand-editable assets, not `.tmp/`), and writes the preview page to `.tmp/logo_lab/index.html`, plus a body-only fragment at `.tmp/logo_lab/artifact.html` for publishing as a Claude artifact. Hand the user the `file://` URL or the artifact link.
4. Tell the user to judge the candidates at true 16 px tab size first — that is the size a browser tab actually gives a favicon, and the lab page puts that comparison first for that reason. Flag the wordmark's measured ~6.26:1 aspect ratio specifically: it is shown for completeness (it is the correct mark for a header, email signature, or share image) but it is not a realistic favicon candidate — the letters go sub-pixel well before 16 px.
5. When the user picks a mark, adopting it means copying the chosen `assets/logo/xoxocom-icon-<name>.svg` file to `sites/xoxocom/app/icon.svg` — Next serves that as the favicon automatically. Record the decision and proceed under `design_website.md` if any further wiring is needed.

### H. Chosen-pages content spec (About + Press/Media, direction locked)

Use this after the user has picked one About direction and one Press/Media direction out of the page prototype lab's six (step F). This round does not offer layout choices — it renders only the two chosen directions — and its entire purpose is to strip out every piece of drafted prose from round F and replace it with a labeled slot, because the round-F prototypes' invented copy (the "why we built this" paragraph, differentiator claims, the founder hero quote, team bios, podcast angles, quote-ready statements, service one-liners) was inaccurate and must never be repeated. **Hard constraint: nothing on these pages is invented prose.** Every text block a human must supply is either a fact already verifiable in the repo, wording the source checklist dictates outright, a functional UI label, or a slot — never a guessed sentence.

1. Confirm which two directions were chosen (currently hardcoded as About = A2, Press & Media = P2 — Option 2 in both rounds, with A1's CTA heading on the About page). Then decide which mode you need: `--mode present` for something to show a stakeholder, `--mode spec` for the internal list of what is still missing. The presentation build is the default because it is what usually gets asked for; run both if you want the spec alongside it (use a separate `--out`, e.g. `.tmp/chosen_pages_spec`, or the second run overwrites the first). If the user picks different directions than what's currently wired in, the script's `PAGES` list and its `about()`/`press()` functions need to be rewritten to match — this is a code change, not a flag.
2. Run: `python execution/build_chosen_pages.py` (or `--out <path>` for a custom location).
3. The script writes `.tmp/chosen_pages/index.html` (standalone) and `.tmp/chosen_pages/artifact.html` (body-only fragment for publishing as a Claude artifact). Hand the user the `file://` URL or the artifact link.
4. Walk the user through what's still open: pick one of the four boilerplate variants and fill it in (every other slot on both pages reuses it verbatim); founding year; the founder's single title, used consistently everywhere; the user's own name as it should appear in print; the product lead's name and role title; LinkedIn URLs; consulting track-record details (years active, client types, logos only with written permission); who the press contact is and at which email; the 3–5 press talkable angles; all photography and product screenshots; the press-kit zip itself.
5. Once the remaining facts are filled in and the founder has signed off, proceed to writing the real Next.js route(s) under `design_website.md`. Note that no directive currently covers adding a route outside the site's existing four-page template, which the new `/press` route will be — flag this to the user if it comes up.

## Edge Cases

- **Unknown brand name**: the script exits non-zero and prints the full list of available brands. Relay the closest matches to the user and ask which they meant.
- **Ambiguous short name** (e.g. `bmw` when both `bmw` and `bmw-m` exist): exact matches win, so `bmw` resolves to `bmw`; tell the user to type `bmw-m` for the motorsport variant. For a true tie with no exact match, the first alphabetical prefix match is used — confirm with the user if it matters.
- **User wants several previews at once**: pass them all in one `--brands a,b,c` run; the contact sheet is generated automatically. Don't run the script once per brand unless they ask for isolated outputs.
- **Library missing / moved**: pass `--library <path>` to point at the `awesome-design-md/design-md` folder. Default is `~/.claude/awesome-design-md/design-md`.
- **Origami lab shapes look invisible in the hero mock-ups**: the hero's radial scrim (`radial-gradient(46% 56% at 50% 46%, var(--color-bg) 22%, transparent 82%)`) swallows anything placed directly behind the headline. Shapes must be corner- or side-weighted, not centred, to read. If a centred layer is wanted, animate it with the standalone CSS `translate` property rather than `transform: translate(...)`, since a keyframe that animates `transform` clobbers a centring transform.
- **Re-running the origami lab with the same flags**: output is byte-identical (deterministic geometry, no randomness) — safe to re-run for a diff check after tuning `--fill-min`/`--fill-max`/`--crease`/`--edge`.
- **Page prototype lab renders in a system font instead of Manrope**: the script inlines the site's real typeface by reading the preloaded latin-subset `.woff2` from `sites/xoxocom/.next/static/media/`, so it needs a prior `next build` (or `next dev` compile) to exist. If that build output is missing, the lab still generates — it degrades to a system sans-serif stack rather than failing. Run a build first if font-accurate review matters.
- **Adding a new full-page prototype to `build_page_prototypes.py` loses its section spacing**: a `:not()` selector's specificity includes its argument, so a broad exclusion selector (e.g. `#a3 section:not(.a3-hero):not(.a3-boiler)`) can outrank a later, more specific per-section padding rule and silently zero out vertical spacing. Scope new per-section CSS by an explicit shared class (the fix already applied: `.a3-sec`) so source order decides the winner, not `:not()` specificity.
- **Chosen-pages content spec: a centred paragraph rule swallows a formula and its note**: round F's boilerplate band centres `.a3-boiler p` for narrative prose. `build_chosen_pages.py` reuses that band to hold the boilerplate formula and a note beneath it, both of which need to read as left-aligned text — the centring rule applies to both classes, so an override must target `.a3-boiler p.formula` and `.a3-boiler p.formula-note` together, not just one of them. This trap belongs to the A3 band and is dormant while the About page is A2, but it returns the moment A3's boilerplate band is reused — keep both selectors together if it is.
- **Chosen-pages content spec: `.section-note`'s negative top margin collides under a hero meta line**: `.section-note` (from round F) carries a negative top margin sized for sitting directly under a heading. Placed under the press hero's meta line (file size / updated date / legal name) instead, the negative margin pulls it into the line above. `build_chosen_pages.py`'s `EXTRA_CSS` overrides this with a positive `margin-top` scoped to `#p2 .p2-hero .section-note` — apply the same override wherever `.section-note` sits under something other than a heading — the About page needs it a second time at `#a2 .a2-product .section-note`, where the note sits under the product one-liner slot rather than a heading.
- **Chosen-pages content spec: the dossier's boilerplate band sizes its own paragraphs**: `#a2 .a2-boiler p` (from round F) sets body-copy size and colour for a narrative paragraph. The boilerplate *formula* and its note are longer and quieter than that, so `EXTRA_CSS` gives `p.formula` and `p.formula-note` their own size and colour rather than letting them inherit the band's rule — otherwise the formula reads as finished copy instead of a template.
- **Chosen-pages content spec: `.a2-end` is a flex row, not a stack**: round F lays the closing section out as heading-left / buttons-right (`display:flex;justify-content:space-between`). The content spec's CTA stacks instead — heading, then the buttons directly beneath it — so `EXTRA_CSS` has to turn the flex row off (`#a2 .a2-end{display:block}`) rather than just reordering the markup, and the `.section-note` beneath the buttons needs the usual positive `margin-top` override.
- **Chosen-pages content spec: `.a2-how`'s accent rule hung off an `h3` that no longer exists**: round F drew each differentiator column's coral top rule with `#a2 .a2-how h3{border-top:…}`. The content spec replaces that heading with a fixed key label plus two slots, so the rule has to move onto `.a2-how` itself (`padding-top` + `border-top`) or the three columns silently lose their dividers.
- **Placeholder or generated text mangles a brand or person's name**: a shared `text-transform:uppercase` label style will mangle exact-spelling names (the former product name `MAtfIT` became `MATFIT` this way; the same applies to any mixed-case brand or a founder's name) — the source checklist requires exact print spelling. Give brand/person-name cells their own non-transformed style (the existing `.label.is-brand` class is the precedent) rather than reusing a transformed label style.
- **Logo lab `--overlap` set too low**: below roughly 0.50, the interlace crossings crowd the X arm tips and the weave has no room to resolve — `build_logo_lab.py` raises a `ValueError` naming the fix (raise `--overlap`, or lower `--stroke`/`--clearance`) rather than emitting a malformed mark. Don't work around the error by retrying with random values; read the message and adjust the named flag.
- **Logo lab `--overlap` out of range**: the script requires `0 < --overlap < 1.0` (as a fraction of one cap square); at or above 1.0 the two X's coincide or invert and the script raises rather than producing a broken icon.
- **Logo lab renders in a system font instead of Manrope**: same mechanism as the page prototype lab — it inlines `sites/xoxocom/.next/static/media/4c9affa5bc8f420e-s.p.woff2` (the site's preloaded Manrope latin subset) and falls back to a system sans-serif stack with an on-page note if that build artifact is missing. Run a `next build`/`next dev` compile first if font-accurate review matters. Note this is a separate mechanism from the wordmark's outlining step below — this fallback affects the lab page's own display type; the wordmark option's font dependency is handled independently (see next item).
- **Logo lab re-run with the same flags**: output is byte-identical (deterministic geometry, no randomness) — safe to re-run for a diff check after tuning `--stroke`/`--overlap`/`--gap`/`--clearance`/`--fused-opacity`/`--wordmark-weight`/`--tracking`/`--wordmark-ink`, including the outlined wordmark.
- **Logo lab wordmark option (`Option D`) is skipped**: `build_wordmark()` needs `fontTools` plus `brotli`/`brotlicffi` (to decompress the `.woff2`) and a readable `--font`. If any of those are missing, the script prints a warning, writes only the three stroke-mark candidates, and the lab page's spec table notes the skip instead of showing Option D. This is a deliberate degrade, not a crash — install the two optional `requirements.txt` dependencies (`fonttools>=4.50.0`, `brotlicffi>=1.1.0`) and re-run to get the wordmark back.
- **Logo lab wordmark tinting**: don't tint the wordmark monogram with the accent color the way the three stroke marks are tinted — its two X's already carry the accent internally as a separate fill, and the remaining letters are painted in `currentColor` for the ink role only. Tinting the whole mark with the accent makes the non-X letters vanish into a single-color blob. The lab page's per-mark `tint: "ink"` role handles this automatically; if adapting the wordmark SVG outside the lab, apply the same rule.
- **Logo lab wordmark aspect ratio**: at ~6.26:1 the wordmark is far too wide for the 16 px favicon slot — its letters go sub-pixel before that size. This is stated on the lab page itself and in the specs table; don't propose it as a favicon candidate. It is the right choice for a header, email signature, or share image, which is why it's in the kit at all.
- **Logo lab with a relative or out-of-repo `--assets-dir`/`--out-dir`**: the script resolves both directories and logs paths relative to the repo root when possible, falling back to the full path when the target sits outside the repo — so a relative or external output location no longer crashes the run (a prior version raised `ValueError` from `Path.relative_to()` in this case; fixed, verified).
- **Logo lab icon SVGs and non-square marks**: the icon wrapper fits a mark to both axes of the icon square (not width alone), so a candidate taller than it is wide would still be contained without overflowing. All four current marks are wider than tall, so width remains the practical constraint for them — this only matters if a future candidate breaks that pattern.
- **Logo lab icon scale precision (resolved, verified)**: `icon_wrap`'s `translate()`/`scale()` transform is formatted with a separate 6-decimal-place formatter, not the 2-decimal-place one used for coordinates elsewhere in the script. A prior version rounded the scale factor to 2dp, which is fine for a coordinate but not for a multiplier — for the wordmark (~9394 font units wide, needing a scale of roughly 0.008), 2dp rounding inflated the factor by about 24% and pushed the mark past the 100-unit icon viewBox, i.e. it would have clipped exactly the favicon/tab test the lab exists to run. Fixed and verified: every current mark now sits fully inside its icon viewBox with equal left/right and top/bottom margins. No action needed unless you're modifying `icon_wrap` itself — then keep coordinates and the scale factor on their separate formatters.
- **Logo lab wordmark glyph drawing (resolved, verified)**: `build_wordmark()`'s entire body — not just the font-loading step — is wrapped in one try/except that returns `None` on failure. This matters because TrueType glyph tables decompile lazily; a malformed or degenerate glyph can raise only when it's actually drawn, which happens after the font loads successfully. Before this fix, such a failure could abort the whole script mid-run and leave every output file unwritten, including the three working stroke marks — not the documented "wordmark-only skip." Verified with a truncated and a garbage font file: the run now completes, skips only the two wordmark files, and still writes all 7 stroke-mark assets.

## Error Handling

- **Proprietary fonts**: previews label the brand's display font but can't load proprietary families (Söhne, figmaSans, etc.), so type falls back to system fonts. Colors and layout are faithful; set expectations that the typeface may differ from the real brand. Stated in each page's footer.
- **Accent is a heuristic**: the accent is the most chromatic color in the palette. For monochrome or prose-format brands it can pick a secondary hue (e.g. Spotify resolves to an orange rather than its signature green). The full palette swatches and the description still show the true brand color — point the user there if the accent looks off.
- **Font lab needs internet to display fonts**: the generated HTML loads Google Fonts via a `<link>` tag. The file generates successfully offline, but the font specimens will fall back to system fonts until the page is opened with an internet connection. This is expected — note it to the user if they're offline.
- **Don't auto-retry `browser-harness`** if its CDP connection drops — re-allow remote debugging in Chrome once, then retry. Generating the HTML never needs the browser; screenshots are a convenience.
- **Page prototype lab — don't invent unconfirmed facts**: never fill in a placeholder (founding year, headcount claims, client names, user/revenue numbers) with a guessed value to make a prototype look more finished — the script's placeholder styling exists precisely so gaps stay visible. Only replace a placeholder in the script once the user has confirmed the real value. The same applies to the drafted quotes and suggested topics the script marks "needs sign-off" — they are drafts for review, not approved copy, until the user or the founder signs off.
- **Chosen-pages content spec — never invent prose, this is a hard constraint, not a preference**: the round-F page prototypes auto-completed many parts of the page with inaccurate or invented information (the "why we built this" paragraph, three differentiator claims and their copy, the founder hero quote, all team bios, four podcast/talkable angles, quote-ready statements, and several reworded service one-liners), and the user's explicit instruction is that this must never happen again. `build_chosen_pages.py`'s only three sources of real text are facts verifiable in the repo, wording the source checklist dictates outright, and functional UI labels — everything else must render through the `slot()`/`val()` helpers, never as drafted sentences. When filling in a slot in the script directly (once the user supplies a real value), copy the user's own words verbatim; do not paraphrase, embellish, or draft on their behalf.
- **Logo lab is a review tool, not an adoption step**: the script never touches `sites/xoxocom/`. Picking a winner is a separate, deliberate action — copy the chosen `assets/logo/xoxocom-icon-<name>.svg` to `sites/xoxocom/app/icon.svg` yourself once the user has actually confirmed a choice from the rendered lab page, not from the SVG files alone (the geometry looks different at true tab pixel size than at full scale).
